## Coordination and timing

Memory A used three fresh contexts with Reader/Librarian/Reader request allocations of 15/16/9. After the pilot, Memory B and C used the same host policy: Reader up to 24, fresh Librarian up to 12 while retaining at least four requests, then fresh Reader with the remaining shared allowance. An early stop with authorized work remaining received a continuation; interrupted summaries are preserved. These allocation changes are part of the host protocol and limit direct comparison with the pilot.

V8 A used a discovery worker and independent reviewer. Two attempts to obtain reviewer capacity were blocked while other root work occupied the host; the coordinator was interrupted and resumed after slots were freed. Its capacity notes and delayed recording remain in the trace. V8 B used one discovery pass and six named reviewer passes: plan, recheck, mutation gate, evidence, remainder and final. The root resumed it after a premature stop at 25 requests. Known successful dispatches and reviewer passes can be counted from retained notes; complete root progress-message, wait-call and failed-dispatch telemetry was not exported. No exact total coordination cost is claimed.

Memory B and C ran concurrently in separate Projects after v8 finished. The root also ran checks and trace analysis. Manifest elapsed time includes preparation-to-dispatch idle time, human/tool scheduling and evaluator stop delay. Candidate activity span measures first through last candidate event, and still includes reasoning and host waits. Server latency measures only the fixture's MCP/Product handling, excluding model reasoning and host tool overhead. These are different measurements. Missing samples are unavailable, not zero.

No outcome improvement threshold was set. These repeated attempts expose completeness and protocol failures; they do not establish a ranking, significance, real-Product discovery completeness or an exactly-once external-effect guarantee.

## Retained failures and interruption cuts

Memory A issued a second unavailable-book POST from an HTTP error handler merely to read the response body. Product events 52 and 53 both returned 409; event 53 has no fresh accepted attempt. The absence of a second created resource does not make this safe. The final skill explicitly prohibits that retry pattern. Most pilot facts were saved before a Journey and never gained a later related fact. One unavailable-rule gap stayed falsely pending because the outcome was attached to its parent action. No ordinary inventory reopening a completed check was observed.

V8 A stopped at 30 requests with ten unused. Three Surfaces were written before any matching visit: POST holds, loan detail and POST desk returns; the last was never visited. Its eight mutation calls have no structured markers because it used the old workflow. That absence is reported as a baseline capability difference, not a violation of instructions that were absent from its frozen skill. Its deliberate repeat branches are distinguishable from a blind retry.

V8 B has thirteen mutation attempts mechanically matched to preceding accepted ids, but that count is not a protocol pass. Generic preparation text did not ground actual preconditions. The malformed unavailable-book attempt was retried under a new name without typed non-execution reconciliation. Per-request action names and a clear retry alias avoided stable item reuse. Successful reserve and check-in facts were saved as plain Observations without resolving their original attempts. Three attempts remain unresolved in final public reads. It also omitted durable readbacks for three observed outcomes. Its SUMMARY counts are stale: the trace and final reads contain 53 Observations, not 36.

The trace cuts preserve the state before request 16 and 32 in Memory A, before request 16 and 27 in v8 A, and at v8 B's evidence-review stop. Memory A had eleven supported facts but only two related-Journey outcomes at the first cut; fourteen facts and two related outcomes at the second. V8 A had zero committed Observations at both cuts, despite Product discovery and mutations. V8 B had nine Observations at its 25-request stop; only the required-book and unavailable-book rejections were completed durable outcomes. Observation count is never used as completed-outcome coverage.

The final memory Reader handoffs also have retained trace cuts. At 24 requests, Memory B had 38 Observations supporting sixteen frozen factual outcomes and three related-Journey outcomes. Memory C had 40 Observations supporting fifteen factual outcomes and thirteen related-Journey outcomes. The final public reads preserve those records. These are handoff snapshots, not separate fresh attempts. Memory B ultimately stopped at 38 requests with two unused; Memory C spent all 40.

Both final Librarian executions sent numeric `103` despite the advertised string `"103"`, producing 404 rather than completing check-in. This is a candidate payload error; the unchanged fixture and the successful string-body check-ins in Memory A and v8 B establish that the frozen outcome remained reachable. Its replacement marker refers to the prior desk context without repeating METHOD/path, so the mechanical matcher leaves that dispatch unmatched. `memory-c/quality-notes.json` records the manual event123 → event124 → event127 correlation rather than borrowing the retired attempt id.

## Recovery evidence

The `interrupted-reservation` pilot used a fresh Agent to reconcile one Library reservation accepted before response consumption. It made six resumed GETs and no new mutation. Its initial evaluator seed recorded the POST Surface before visiting that operation, so it is narrow recovery evidence with a Surface-grounding defect in the seed.

The stronger `actions-recovery` proof uses the shared tested reservation Product, an actually visited Reserve page, and a fresh Agent, Chromium page and MCP session after Product acceptance. Its validator confirms one reservation, no repeated Reserve, separate empty-Reason and valid cancellation outcomes, one resumed cancellation POST, and zero final uncertainty. Browser-required validation prevents the empty form from reaching HTTP; the deterministic acceptance suite separately checks the server's 422 rejection. The candidate's summary undercounts six rejected MCP calls as four and omits a root-route not-found response. Both corrections are retained in the validation/report, without rewriting the candidate's account.

The automated suite covers twelve controlled interruption cases: six boundaries for creation and cancellation, all committed-token replays, late old outcomes and Product-side mutation counts. The fresh-Agent trace covers one acceptance/unread-response boundary through the full Actions path. Neither is an OS process-kill test. Ordinary recorded Test Runs have their own execution contract and do not carry Explore attempt authorization.
